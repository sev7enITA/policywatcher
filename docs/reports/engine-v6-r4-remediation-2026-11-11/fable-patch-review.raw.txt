## 3. Patch blockers

### PR-01 (P0): the live model path cannot make a single call

**Mechanism.**

1. `src/lib/engine/claims.ts:139` builds the client with an API key only, which is the Gemini Developer API mode. The r4 harness asserts the same host (`scripts/engine-o2-r4-wave.ts:50`).
2. `claims.ts:140` now calls `countTokens({ model, contents, config: { systemInstruction: system } })`.
3. In the installed SDK, `countTokens` takes the Developer API branch (`index.mjs:16732-16733`), which calls `countTokensConfigToMldev` whenever `config` is present (`index.mjs:9891-9894`). That function throws if `systemInstruction` is defined (`index.mjs:9836-9840`): "systemInstruction parameter is only supported in Gemini Enterprise Agent Platform mode, not in Gemini Developer API mode."
4. The throw happens before any HTTP request. The new `.catch` at `claims.ts:140` converts it to `model_transport_error` (`failures.ts:16`), because the error has no status and is not an abort.
5. `model_transport_error` is retryable, so each analyze or verify task spends three attempts, then ends as a terminal failure with a review, and repeats on the next cycle.

**Consequence.** With this candidate no analyst or verifier request reaches the provider. The durable code blames transport, which would misdirect diagnosis of exactly the verifier problem O2 is trying to isolate.

**Why the tests pass.** `engineModelRuntime.test.ts:51-55` mocks the SDK and asserts that `config.systemInstruction` is passed. The test encodes the broken call.

**Effect on the prepared harness.** All twelve cases would end with an error and zero HTTP receipts. The two-failure stop rule lives inside the fetch wrapper (`engine-o2-r4-wave.ts:69-74`), so it would not trigger. No quota would be spent, but the wave would produce nothing.

**Inaccurate closure claim.** README line 16 ("Count the system instruction in the input budget") and register N06 ("full system instruction counted") describe behaviour that the installed SDK does not allow in this mode.

**Falsifier.** An offline test that builds the real `GoogleGenAI` client with a dummy key, replaces `globalThis.fetch` with a stub, and calls `liveAnalysis.analyze`. If the stub receives a `:countTokens` request, I am wrong. No network or key is needed.

**Correction.** Do not pass `config.systemInstruction` to `countTokens` in API-key mode. Count the system text as part of the counted contents (for example a two-part contents array), which is a conservative upper bound. Add the offline test above so the SDK's own converters are exercised. Map locally rejected arguments to a distinct non-retryable code instead of `model_transport_error`.

### PR-02 (P1): a remembered assessment can outlive its review

**Mechanism.**

1. Day 1: content A is analysed and held, for example `high_impact_review_required`. `hold()` creates review R1 and stores the memo (`pipeline.ts:109`).
2. Day 2: acquisition is ineligible (`acquisition_failed`, `live_source_unverified`, a contract mismatch). `evaluate` holds at the top with no checkpoint. Because the evidence key contains the task ID, a new review R2 is created and **every** pending or observed review for the policy is superseded, R1 included (`pipeline.ts:97-103`). The memo is untouched: only the unchanged path, refresh, rebaseline request and baseline approval clear it (`pipeline.ts:150, 379, 447, 465`).
3. Day 3: content A again. The key matches and the earlier task is completed, so the task finishes as `assessment_already_recorded` (`pipeline.ts:177-193`). No review is created.

**Consequence.** R1 stays superseded for as long as the content stays A. The only open review is R2, an acquisition failure that cannot be approved. In publish mode a validated high-impact change is silently parked until someone thinks to "refresh" an unrelated review. In observe mode the review records that O2 would use as evidence end on the acquisition failure. In r3 day 3 would have re-raised the change. Acquisition failures are the most common non-success outcome in the retained evidence, so this sequence is ordinary, not exotic.

**Not covered by tests.** The reuse tests never interleave a different hold between two observations of the same content.

**Falsifier.** A test: assess content (hold), run one cycle with an ineligible capture, run a third with the original content, then assert there is a pending or observed review whose reasons are the semantic ones. On the current code I expect it to fail.

**Correction (either is sufficient).**

- In the reuse transaction, also require that the review for `assessedTaskId` is still `pending` or `observed`, or that the earlier outcome was `observed_change_ready`; otherwise fall through to a new assessment.
- Or clear `assessedKey`/`assessedTaskId` in `hold()` whenever it supersedes reviews without remembering the current task.

## 4. Other introduced weaknesses

### PR-03 (P2; blocker before any publish-mode use): non-content holds are memoised

- `evidence_stale` (`pipeline.ts:318`) is a statement about elapsed time, yet it is remembered because it is not in `REASSESSABLE_FAILURES` (`failures.ts:25-28`). A fresh capture would cure it; the memo prevents that until a manual refresh. With a verifier backlog this would be a frequent outcome.
- `verification_model_identity_missing` (`claims.ts:112`) depends on a provider response field, not on the content, and is also remembered.
- Approval requires evidence no older than two days (`pipeline.ts:402`). r3 regenerated the review every cycle; r4 does not, so a pending high-impact review becomes unapprovable after two days and then needs a manual refresh plus two new cycles. The code comment at `pipeline.ts:180-181` shows this is intended; it should be stated in the README as a reviewer deadline, and the two reasons above should be reassessable.

### PR-04 (P2): transport-bound confirmation has no exit

- The candidate fingerprint now includes `observation.source` and `observation.finalUrl` (`pipeline.ts:197, 205, 209`). If a source alternates between direct and rendered transport, or its final URL varies between fetches, the two observations never match, the candidate is reset each cycle and the task ends as `confirmation_pending` indefinitely.
- No review is ever raised, and `pipeline.ts:204` records the attempt as verified, so in publish mode the policy shows a fresh successful check while a detected change waits forever.
- The binding itself is a sound tightening. What is missing is a bound: after a small number of same-content, different-transport observations, hold with an explicit reason.
- The same fields are in the assessment key, so a source that flips transport after assessment is re-analysed on each flip. For such sources finding N03 is not closed.
- Upgrade effect, benign: candidates stored in the r3 fingerprint format will not match once, costing one extra confirmation cycle.
- How often real sources alternate is unmeasured.

### PR-05 (P2): terminal-failure reviews accumulate

- `terminalFailure` creates a review keyed on the task ID and does not supersede earlier ones (`store.ts:282-286`). A failure that persists (verifier 5xx or deadline after three attempts, lease exhaustion) therefore adds one more review per policy per cycle. They are cleared only by the next `hold()` or an unchanged capture.
- Review-class failures raised before a checkpoint exists take the same path: `comparison_budget_exceeded` from `pipeline.ts:231`, `artifact_size_limit`, `document_size_out_of_bounds`. They are deterministic for the content, are not remembered, and recur daily. A heavily rewritten policy, which is exactly the case that most needs a reviewer, produces a new review every day. Register N04 already says some pre-checkpoint failures lack a reusable decision; the duplicate reviews are the part it does not mention.
- The analyst result of a task that fails terminally at verification is discarded and regenerated on the next cycle.
- Correction: key terminal reviews on policy, mode, baseline and reason, or supersede earlier terminal reviews; route deterministic pre-checkpoint failures to a remembered hold.

### PR-06 (P2): 429 handling and the Retry-After claim

- The SDK's `ApiError` carries only `message` and `status` (`index.mjs:7763-7770, 14273-14279`). `modelFailure` looks for `error.headers` (`failures.ts:10-13`), which is never present, so `retryAfterMs` is always 0 with this SDK. The test at `engineV6.test.ts:1090` injects an `EngineModelError` directly and does not show otherwise. README line 14 and register N05 should say the delay is not available from the installed SDK.
- Every 429 is a review hold for the cycle (`failures.ts:22`, `pipeline.ts:345-347`). A per-minute limit is treated like daily exhaustion: the task is closed, the candidate is cleared, the analyst result is lost and two new observations are needed. r3 would have retried after backoff.
- The hold is correctly not remembered, and it no longer burns three attempts. There is still no circuit breaker: each remaining queued task sends one request and collects its own 429. That is the open scheduling gap (N06), not a new defect.

### PR-07 (P2): backup transaction

Correct as written: a missing `$transaction` is refused, a failed transaction is not retried table by table, a missing migration ledger is reported as `null`, and restore is still not claimed (`encryptedBackup.ts:132-174`).

Open points:

- The transaction has a 60-second limit and reads every table into memory, including `EngineArtifact` with raw captures of up to 12 MB each. Once the export exceeds 60 seconds there is no backup at all. That is the safe direction, but the ceiling is unmeasured.
- Whether a 60-second export delays or fails worker transactions on the SQLite host (15-second fenced transactions, 5-second busy timeout) is unmeasured. I did not read Prisma's transaction internals, so I make no claim either way.
- `provenance` is written but `validateCompleteBackupPayload` (`encryptedBackup.ts:217-271`) neither requires nor checks it, so verification passes with or without it.
- `consistency: 'serializable-transaction'` is an assertion about the request made, not a measured property. The integration test at `engineV6.test.ts:1141` uses a database with no concurrent writer.

## 5. Checked and found correct

- **Fencing of the reuse path.** The reuse decision is re-validated inside the fenced transaction: `currentPolicy` plus a compare-and-set on `assessedKey` and `assessedTaskId` (`pipeline.ts:182-188`). A concurrent refresh makes the task fail with `assessment_context_changed`, which is retryable; the retry sees the cleared memo and starts a new candidate. `fenced`, `transition`, `finishTask` and `advanceTask` are unchanged from r3 apart from the import.
- **Invalidation.** The memo is cleared on an unchanged capture, explicit refresh, rebaseline request and baseline approval. A new candidate produces a different key. Publication does not store a memo, and the baseline change invalidates any older one. Reassessable failures are not remembered. Changing either configured model alias or the build changes the key.
- **Freshness.** A pending high-impact review no longer marks the policy as successfully checked (`pipeline.ts:89`).
- **Terminal failures.** A review is retained through an idempotent upsert; `EngineReview.taskId` is unique and a failed task has no earlier review. The policy row, including `updatedAt`, is preserved in observe mode (`store.ts:275-276`).
- **Bounded diagnostics.** Provider message text is discarded; only `model_http_<status>`, `model_deadline_exceeded` or `model_transport_error` is stored (`failures.ts:5-17`).
- **Migrations and parity.** Both migrations are the same two additive nullable columns (identical hash). `prisma/schema.prisma`, both readiness lists and both CLI-free initialisers carry them. `build-db.log` shows the initialiser adding both columns to a fresh file.
- **Manifest.** 122 files; every per-file hash and the top hash recompute to the declared values; my approximate import closure matches the listed set exactly. Migrations, lock files, both initialisers, backup and readiness code are now included. The harness pin equals the manifest hash.
- **Readiness.** PostgreSQL integrity and foreign-key values are reported as not measured instead of passed; the engine block reports configuration presence with `qualification: 'not_assessed'`.
- **r3 material.** By plain `diff`, the r3 harnesses, corpus, reports and evidence are byte-identical in this checkout. The three audit files under `docs/reports/engine-v6-external-audit-2026-11-11/fable/` are byte-identical to my originals.
- **Stated boundary.** The README and register state that O2, completeness, semantic accuracy and 500/day remain unqualified.

**To verify on an isolated copy, not a defect.** The CLI-free initialisers add the columns but write no migration-ledger row. On a database that has a ledger, readiness may report the new migration as missing after an initialiser upgrade. This is the same pattern as the r3 claim-ledger migration.

**Prepared but not evidenced.** The PostgreSQL contract smoke additions read correctly, but no log of a run was provided, and I ran nothing.
