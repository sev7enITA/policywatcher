### 3.1 PR-01: the model call path

- `countTokens` no longer receives a `config`. The system text and the payload are counted as two parts of one content (`claims.ts:140`). The SDK converter that rejected the old call runs only when `config` is present, so it is no longer reached.
- `generateContent` still sends the system text as a system instruction, which the Developer API mode supports.
- A locally rejected argument now maps to `model_request_invalid`, a non-retried, non-remembered review failure (`failures.ts:15, 23, 29`), instead of a transport error.
- `engineRealSdk.test.ts` builds the real client with a dummy key and a stubbed `fetch`, and asserts one `:countTokens` and one `:generateContent` request. It is the falsifier I proposed.
- `fable-regressions-before.log` shows that test failing on the old code with `model_transport_error` at `claims.ts:140`; `fable-regressions-final.log` shows it passing. The mocked unit test no longer asserts the unsupported argument.

Residual: the count treats system text as user content, so it is an estimate of the request size. That is adequate for a budget gate.

### 3.2 PR-02: memo and review liveness

- Every `hold()` now clears the memo before deciding whether to store a new one (`pipeline.ts:90-91, 111`). An acquisition hold therefore invalidates the earlier assessment.
- A terminal failure does the same (`store.ts:282-285`).
- The interleaved test (`engineV6.test.ts:1183-1197`) fails in both modes on the old code and passes on the new, per the retained logs.

Traced by hand: assess, then acquisition hold, then the same content gives a new candidate, a confirmation and a new semantic review. The earlier review stays superseded and its ledger rows remain.

### 3.3 PR-03: non-content holds and expiry

- `evidence_stale`, `verification_model_identity_missing` and `verification_model_not_independent` are now reassessable (`failures.ts:27`).
- Reuse requires the remembered task's capture to be less than two days old and not in the future (`pipeline.ts:181-183`). After that the content is confirmed and analysed again without manual action.
- Tests at `engineV6.test.ts:1200-1217` cover both.

### 3.4 PR-04: transport-bound confirmation

- A same-content observation whose transport fingerprint differs from the stored candidate is now an explicit hold, `confirmation_transport_changed` (`pipeline.ts:201-204`). An alternating source produces a visible review every second cycle instead of a silent loop.
- A capture awaiting confirmation is no longer recorded as a successful check (`pipeline.ts:212`).
- Test at `engineV6.test.ts:1218-1225`.

### 3.5 PR-05: terminal-failure reviews

- A terminal failure supersedes the other active reviews of that policy and mode and keeps the failed tasks as history (`store.ts:282-284`). Test at `engineV6.test.ts:1226-1239`: one active review, one superseded, two failed tasks.
- Still true, and stated in register N04: a deterministic failure before the first checkpoint (for example `comparison_budget_exceeded` at `pipeline.ts:239`) is not remembered. It recurs each cycle and adds a history row each time, with one active review.

## 4. New findings

### FR-01 (P2): r3 candidate state is misread at upgrade

**Mechanism.** r3 stored the candidate fingerprint as a hash of profile and contract. r4 stores a hash that also includes transport and final URL. `pipeline.ts:202` treats any stored fingerprint that differs from the new one, for the same content hash, as a transport change and holds.

**Consequence.** On a database that already holds r3 engine state, every policy with a stored candidate and unchanged content gets one `confirmation_transport_changed` review on its first r4 cycle, although its transport did not change. In observe mode r3 leaves the candidate in place after a clean observed change, so this covers every diverged policy, not only those awaiting confirmation. Each such hold also supersedes that policy's active review. It heals after one cycle, but it puts false reasons into the review record that O2 would read as evidence.

**Also.** The fingerprint includes the contract and profile hashes, so a legitimate contract edit while a candidate is pending is labelled a transport change too.

**Status.** Confirmed by code. No fixture has r3-format state, so no test covers it. The number of affected rows on any real database is unknown to me.

**Correction (any one).**

- Run r4 only on a fresh isolated database, and say so in the deployment note.
- Or clear candidate fields in the upgrade step.
- Or hold only when the stored fingerprint is in the r4 format and differs in transport, and otherwise reset the candidate.

### FR-02 (P2): public status now degrades on a first changed capture

**What changed.** r3 had an adjudicated regression test, "records eligible pending evidence without degrading public availability", expecting `Available` after a first changed capture (r3 `engineV6.test.ts:724-729`). r4 renames it and expects `Needs Review` (r4 `engineV6.test.ts:724-729`), because `pipeline.ts:212` now records the attempt as unverified and `pipeline.ts:74-75` writes that status in publish mode.

**Consequence.** In publish mode a single odd capture (an A/B variant, a transient CDN response) marks the policy "Needs Review" until an unchanged capture or a published change. That status string is used by public components (`src/components/PolicyDetails.tsx`, `src/app/DashboardClient.tsx`). I did not trace how they render it.

**Why it is not a merge blocker.** Observe mode never writes these fields (`pipeline.ts:73`), and publication is not authorised.

**What I asked for.** PR-04 asked for a bound on unconfirmed alternation. Not advancing the success date is consistent with that. Changing the public status is a further step that reverses an earlier adjudicated decision, and README line 34 mentions only freshness.

**Decision needed from the owner before publish mode.** Either accept the new behaviour and record the reversal, or keep the status unchanged while a candidate awaits confirmation and only withhold the success date.

### FR-03 (P2): reuse now lasts two days, so re-analysis continues at a lower rate

**Mechanism.**

- Observe mode, clean observed change: the candidate is not cleared at commit (`pipeline.ts:329-340`). When the memo expires, the stored candidate confirms immediately and the policy is analysed and verified again. Cadence: every second daily cycle, for as long as the source differs from the baseline.
- After a hold (either mode): the candidate was cleared, so expiry costs one confirmation cycle and then a new analysis. Cadence: about every third daily cycle. Between expiry and the new review, the pending review cannot be approved because its evidence is older than two days (`pipeline.ts:410`).

**Consequence.** With U unresolved diverged policies, steady demand is roughly U/2 to U/3 verifier calls per day. Against the 20 verifier requests per day observed on 8 November, that saturates at roughly 40 to 60 unresolved policies. This is arithmetic from the code and one dated quota observation, not a measurement.

**Status.** Design consequence of the PR-03 correction, not a defect. Register N03 already says no cost reduction is measured, which is accurate. It should not be read as closed. The 500/day design must budget for it.
